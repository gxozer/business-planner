# Use Cases Template

A companion document to the business plan: concrete scenarios of the target customer actually using the product to get value — not personas, not a feature list, but Actor → Trigger → Scenario → Outcome. This is what makes "target segment" and "solution" tangible instead of abstract.

Draw the actors from the target segments in Market Analysis and the domain-specific intake answers (`references/domain-questions.md`) — don't invent generic ones.

## Primary Use Cases

One to three per core target segment, each structured as:

### <Use case title — named for the outcome, not the feature>

- **Actor**: the specific customer/user (a role or segment, not "the user").
- **Trigger**: the situation or moment that sends them looking for something like this.
- **Scenario**: what they actually do with the product, in a few concrete steps.
- **Outcome**: the value or result they walk away with.
- **Exercises**: which part of the business model this touches (a pricing tier, a core feature, a channel) — optional, only if it adds information.

## Secondary / Edge-Case Use Cases

A couple of scenarios that stress-test the value proposition rather than showcase it — an unusual but plausible situation, a competitor's customer switching over, a lapsed user coming back. These are useful precisely because they're where a shaky idea shows its cracks; don't only write flattering scenarios.

## Sources

- Anything used to ground a use case in reality rather than invention (a research finding, a domain-question answer, a comparable product's documented workflow).
